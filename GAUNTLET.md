Constraint state for this server (SSoT). Created by `/gauntlet convert` 2026-07-29. Operator owns §1 and §5; Claude maintains §2–§4 and §6, transcribing operator rulings only.

## §1 Oracle — done-definition

- **It is**: a stdio MCP server over the U.S. DOL Wage and Hour Division enforcement dataset. Tools — `employer_violations`, `back_wages_summary`, `violations_by_state`, `top_cases`, `flagged_employers`, `case_detail`. Six, which is what `test/server.test.ts` *"lists exactly the six documented tools"* asserts and what both channel probes check; this line named four from the 1.1.0 release until 2026-09-14. It exists so that employer wage-theft history, back wages owed, civil penalties and affected-employee counts are answered from WHISARD rather than recalled.
- **DONE means**: (a) an MCP client sees every tool and a real lookup round-trips over stdio; (b) results carry the underlying values so a caller can cite rather than trust; (c) every upstream request is serialized, spaced, timed out, and identifies itself.
- **Non-goals**: predicting enforcement outcomes, naming individuals, any claim about a current employer relationship.

- **MUST NEVER** (operator, 2026-07-29): *"Stale data presented as current."* WHD publishes concluded investigations, late. A 2019 case is not an employer's present compliance state, and an empty result is not a clean record. Every answer is exactly as current as its newest row and must say so. Locked by SPEC `vintage-on-every-answer`.

⚠️ The three bullets above the MUST NEVER line are still transcribed from the README rather than elicited; the MUST NEVER clause is operator-authored.

## §5 Acceptance specs

### SPEC vintage-on-every-answer
```
Given WHD enforcement data, which lags and records concluded investigations
When any tool returns a result
Then the result reports the newest findings date actually present in it
```
Computed from the returned rows, **never from the clock**. A generated-on timestamp would assert the opposite of the truth and is itself the bug: it would stamp "today" on a 2019 record. The empty case reports `null` rather than omitting the field, because an answer with no dates is the one most likely to be read as current.

Check: `test/server.test.ts` (tagged `spec: vintage-on-every-answer`), three cases — the note, the newest-date computation across a mixed set, and the no-dates case. **Red-capable:** written RED first; all three failed before `withDataCurrency` existed (2026-07-29).

⚠️ **`back_wages_summary` satisfies this SPEC by DISCLOSURE, not by accuracy, and the distinction is the whole finding.** Its `latest_findings_end` is the max over the rows it summed, and those are the `max_cases` LARGEST cases — an arbitrary subset in the date dimension, which no `sort_by` can fix. Measured over three matching rows ($900,000 ending 2001, $500,000 ending 2003, $10 ending 2026) at `max_cases` 2: the answer states 2003, and the 2026 case arrived in the same page as the probe row and was dropped undated. Capping is the ordinary path for a populous jurisdiction rather than an edge case: `{st_cd eq "NY"}` returns 1001 rows at an ask of `cap`+1, so a default NY summary caps — though not universally, since WY returns 853 and VI 92 on the same ask (all three measured 2026-09-15, after the first draft of this paragraph asserted that *any* state-only query exceeds the cap and the probe said otherwise). Fetching the true newest date would take a second request against the throttle on every capped call; naming the population costs nothing, so a capped answer now says in its `note` that the date is the newest among the `max_cases` largest cases only and that the newest matching case may be far more recent. Pinned by the C1 case, mutation-probed both ways (suppressing the qualifier reddens it; making it unconditional reddens the uncapped case, and only that one).

### 2026-09-14 — fix round 2: a guard that validated the shape and not the thing

Four findings against fix round 1, and three of them are the same defect in different clothes: an input a caller can get slightly wrong reaches DOL as a legal-looking filter, comes back 204, and is rendered as `count: 0` under the note that an empty result is not a clean record. That answer is indistinguishable from a real absence, which on this dataset reads as "no wage theft here."

- **The transposed-window guard could be walked around, by the same input class it was built for.** `normDate` checked `\d{4}-\d{2}-\d{2}` and stopped; `shiftIsoDate` goes through `Date.UTC`, which ROLLS an out-of-range component over rather than rejecting it; and the bound-order check compares the RAW argument strings. So `{found_after: "2024-01-99", found_before: "2024-02-01"}` sorts in order, passes the guard, and builds `gt 2024-04-07T23:59:59 AND lt 2024-02-02T00:00:00` — the exact unsatisfiable filter the guard exists to refuse. Single bounds were as quiet: `"2024-13-45"` queried `gt 2025-02-13` and `"0000-00-00"` queried `gt 1899-11-29`, with the query echo still reporting what was typed. Nothing in the suite fed a calendar-invalid date; the malformed-date case used `"January 2024"`, which the shape regex already caught.
- **`normState` accepted any two letters**, so `{st_cd eq "ZZ"}` was a legal filter and NU-for-NV was a confident zero. Closed rather than narrowed, because unlike the `LIKE` case residue this domain is closed: the Census FIPS/USPS reference gives 57 codes, and one `not_in` over all 57 answers 204 across the whole dataset — so the allow-list cannot refuse a code WHISARD holds. The probe was shown red-capable first (the same filter with `NY` removed returns NY rows), since a 204 is also what a malformed filter looks like.
- **`has_more` and `note` disagreed on two tools of four.** `top_cases` returned no `note` key at all and `flagged_employers`' note was a static flag-semantics string that never varied with truncation, while `employer_violations` and `violations_by_state` spelled it out. The boolean was always right; a caller reading the prose half — a human, or a model summarising the answer — learned about truncation on half the tools.
- **Dropping the column projection moved the cache's ceiling without moving its bound.** `DOL_CACHE_MAX` counts ENTRIES, and an entry became up to `max_cases`+1 whole rows: ~2.8 MB each, ~840 MB at the default 300, in a stdio process whose whole job is to stay up. The README named the hazard in the same paragraph that left the default unbounded, and the eviction test ran `DOL_CACHE_MAX=2` over empty result sets, so no test pinned any size relation at all.

**And the round settled the standing gap, in one request, once quota came back.** DOL's `LIKE` does **not** honour `\` as an escape: `{trade_nm like "%Kevin Misc\h%"}` answers 204 while the control `"%Kevin Misch%"` answers 200 with both rows in the same minute. That is the direction that fails — `escapeLike`'s output is a pattern hunting a literal backslash, so a term containing `%`, `_` or `\` matches nothing. Recorded, not repaired: `LIKE` has no other way to make `%` literal and DOL exposes no `ESCAPE` clause, so the repair is a design choice and belongs to its own change.

Rungs: 97 tests, both typecheck passes, and `npm run smoke` 9 passed / 0 failed / 0 upstream / 0 skipped against a live key.
